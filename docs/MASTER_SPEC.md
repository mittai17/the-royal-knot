# WEDFLOW – THE ROYAL KNOT — MASTER ERP SPEC (user-supplied, authoritative)

The user supplied this master specification on 2026-11-01. It is condensed here; the full text is the user's message. Where it conflicts with docs/WEDFLOW_SPEC.md (screenshots) the MASTER SPEC wins. Source priority: original PDF business rules > approved roles/tech > Excel workflows > UI images.

## Hard decisions
1. Roles (exact codes): FOUNDER, PLANNER, FINANCE, EVENT_MANAGER, OPERATIONS, CLIENT, VENDOR, SYSADMIN. NO generic ADMIN (rename ADMIN -> FOUNDER). No other roles.
2. Agreement must be SIGNED before the client sees vendor shortlist or floor plans (client portal vendors/floor-plan hidden until signed).
3. Draft wedding workspace (internal, not a booking, never counted in revenue/completed stats) vs Confirmed wedding (only after: agreement signed + final proposal accepted + booking deposit verified). Keep SEPARATE fields: booking status (DRAFT, AGREEMENT_PENDING, PROPOSAL_PENDING, DEPOSIT_PENDING, CONFIRMED, CANCELLED), execution stage (INITIAL_PHASE, VENDOR_BOOKING, PLANNING, EVENT_DAY, FINANCIAL_CLOSEOUT, COMPLETED), financial status. UI tabs (All/In Planning/In Progress/Completed/Cancelled) are derived filters.
4. Vendor sequence: Qualified enquiry -> consultation -> agreement signed -> RFQs -> quotations -> comparison -> client vendor selection -> selected vendor -> final proposal -> client acceptance -> booking deposit -> confirmed. Selecting a vendor auto-closes competing RFQs with decision history.
5. Auto-planning ONLY after confirmed + verified deposit: Full-Service >= 26 tasks; Partial / Day-of gets a reduced scoped set (Day-of is a subtype of Partial, not a third primary package).
6. Payment milestones configurable per contract (no hardcoded %; 20/40/40 is demo config only).
7. Financial separation: client invoice vs client payment vs vendor bill vs vendor payment vs expense vs extra charge vs reconciliation — separate modules, never mixed. Vendor Payments is its own module (REQUESTED, APPROVED, SCHEDULED, PROCESSING, PAID, FAILED, CANCELLED) separate from Vendor Bills (DRAFT, SUBMITTED, VERIFIED, APPROVED, PARTIALLY_PAID, PAID, REJECTED).
8. One canonical module per domain; role-aware views of same route. Legacy redirects: /todays-events -> /command-centre?view=today ; /vendor-checkin -> /command-centre/vendor-checkin ; /checklists -> /tasks?view=checklists ; /updates -> /activity ; /quotations -> /procurement?tab=rfqs. Checklists live inside Planning & Tasks; Today's Events/Run Sheet/Vendor Check-in live inside Event Command Centre; Updates & Reports renamed Activity Feed (/activity); Quotations+POs inside Procurement.
9. Canonical states: Lead NEW, INITIAL_CONSULTATION, PROPOSAL_SENT, NEGOTIATION, CONVERTED, LOST. Agreement DRAFT, SENT, SIGNED, REJECTED, EXPIRED. Quotation DRAFT, SENT, RECEIVED, UNDER_REVIEW, COMPARED, SELECTED, REJECTED, CLOSED, EXPIRED. Task TO_PLAN, IN_PROGRESS, DONE, BLOCKED (+ derived overdue). Client payment PENDING, PROCESSING, SUCCEEDED, FAILED, REFUNDED. Invoice DRAFT, SENT, PARTIALLY_PAID, PAID, OVERDUE(derived), CANCELLED. RSVP PENDING, CONFIRMED, DECLINED. Vendor arrival EXPECTED, ON_THE_WAY, ARRIVED, DELAYED, COMPLETED. Room allocation PENDING, CONFIRMED, CHECKED_IN, CHECKED_OUT, CANCELLED. Incident REPORTED, TRIAGED, ASSIGNED, IN_PROGRESS, RESOLVED, CLOSED. Transitions enforced in backend.
10. Approvals: one Approval model (reference, source module/record, wedding, initiator, amount, reason, approver, status, supporting doc, created/decided time, notes). Maker-checker: a creator cannot approve their own request (Planner own expense, Finance own payment request). Founder approves exceptions; Planner proposes only; Event coordinator reports extra costs only; SYSADMIN never approves business payments.
11. Financial integrity: Decimal everywhere, idempotency keys, transactions, no deletion of posted records (reversal/correction entries), audit of every financial op, reconciliation matches quotation+PO+bill+advances+approved extras and flags duplicate bill refs, qty/rate diffs, unapproved extras, overpayments.
12. Security tests required (15): couple A vs B; vendor A vs B quotation; coordinator cannot approve vendor payments; team member unassigned records; planner own request; finance maker-checker; vendor cannot see other wedding invoices; sysadmin cannot execute payments; API bypass of frontend; IDOR; unauthorized MinIO download fails; socket room auth; repeated gateway callbacks no duplicate payments; repeated booking confirmation no duplicate project; repeated task generation no duplicates.
13. Demo data: 25 weddings, 400-500 guests, ~18 vendors each, 3 competing caterer quotes, labelled DEMO.
14. Required docs: requirements traceability register, ER diagram, permission matrix, role manuals, architecture doc, demo script.
